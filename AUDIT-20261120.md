## 1. Strong parts

**The conformance test harness is the single best thing in this repo.**
`test/metacredo/check_conformance_test.exs` parses every check's own
`explanations[:examples][:wrong]` snippet through the real Metastatic adapter and
asserts the check actually fires — and that it stays silent on the `:correct`
snippet. This is a doc-drift invariant, not a smoke test: it makes the 72
checks' public documentation executable. The file's own comment records that it
"found and drove fixes for sixteen checks that were silently dead on real Elixir
code." The `known_adapter_defect?/1` guard (`@capture_shorthand`,
`@remote_pipe`, `@pseudo_code` regexes) is the right call — it skips examples the
upstream adapter mis-parses rather than working around the adapter inside the
tool, and it documents *why* at the top of the file.

**`MetaCredo.Check.Utils` is a real type boundary, not a grab-bag.**
`safe_stdlib_call?/1` (`lib/metacredo/check/utils.ex:196`) splits a qualified
call into `{module, function}` and consults `@safe_modules`/`@safe_bare_functions`
before any heuristic runs. That single predicate is what stops `Keyword.get`
being flagged as an HTTP "get" and `Map.fetch!` as a database "fetch".
`line_of/2` (line 148) exists specifically because Metastatic does not attach
`:line` to every node — the docstring spells out that `if`-derived
`:conditional` nodes arrive with empty metadata, so checks that read
`meta[:line]` directly emit `line_no: nil` and break `explain file:line`, the
snippet renderer, and GitHub annotations. That is a defect class closed by
construction.

**`test/metacredo/check/classifier_boundaries_test.exs` is the precision half of
the story.** Where the conformance test proves recall, this file proves
*precision* on the exact names that trip naive heuristics: `do_stop_instance`,
`stop_owned_port`, `per_project_enabled?`, `start_link`,
`activate_loaded_project` must produce zero `ImperativeStatusHandling` findings;
`log_dllb_output`, `get_state`, `Dllb.Query.update`, `Ecto.Query.where` must
produce zero `SyncOverAsync` findings. The `"module-level limiter declarations
apply only to that module"` test (asserting `issue.line_no == 6`) pins
module-scoping of `plug PlugAttack` — that is an ownership invariant expressed as
a test.

**`MetaCredo.Git` defends an argv boundary it does not control.**
`@ref_pattern`/`@filter_pattern` (`lib/metacredo/git.ex:186-200`) validate
base/head/filter before they reach `System.cmd/3`, with the comment stating
plainly that even though argv entries never pass through a shell, a ref beginning
with `-` would still be read as an option. `parse_unified_diff/1` keys on
`+++ b/` and treats `+++ /dev/null` as a deletion, so `--diff-lines` cannot
attribute findings to a removed file.

**`MetaCredo.Baseline` is deliberately not keyed on line number.** `key/1` uses
`{check, filename, line_no, message}`, and `baseline_test.exs` has an explicit
`"does not match on line number alone"` test. The docstring explains the
reasoning: a finding that moved but did not change is still pre-existing.
`filter/2` treats a missing baseline as empty rather than hiding findings —
fail-open in the safe direction, and tested.

**`MetaCredo.Sources.parse_all/1` bounds concurrency deliberately.**
`@max_parse_concurrency 8` with the comment that each task holds a full AST in
memory and a 24-core CI runner should not spawn 24 parsers. `Task.async_stream`
with `timeout: 30_000, ordered: false` plus a three-clause reducer that handles
`{:ok, {:error, _}}` and `{:exit, _}` means one unparseable file degrades to a
`Logger.debug` and a skipped file, never a crashed run.

**The `Execution` pipeline is a readable, linear `|>` chain**
(`lib/metacredo/execution.ex:66-78`): flat_map → filter_disabled_by_comments →
maybe_filter_strict → maybe_filter_confidence → maybe_filter_changed_lines →
sort_issues. Each stage is a named single-purpose function with a `nil`/`false`
no-op clause, which is why `execution_test.exs` can test `min_confidence`,
`changed_lines`, and the `test/` exclusion independently. The
`lift_test_exclusion` flag is documented as distinguishing a *machine-derived*
file list (diff mode, `false`) from a *deliberate user opt-in*
(`--path test/`, `true`) — that is a subtle distinction most tools get wrong.

**`Config.default_disabled_checks/0` is an honest curation with reasons.** Each
entry carries a comment naming the unsound heuristic: `PathTraversal` flags
`format_issue` because it contains "rm", `params_get` because it contains "get".
A linter shipping its own false-positive post-mortem in the source is exactly
right.

## 2. Weaknesses & glitches to fix

### 2.1 **Defect** — `Analysis.DeadCode` only recognises `:early_return`, so `raise`/`throw`/`return` produce no finding

`lib/metacredo/analysis/dead_code.ex:74` — `check_block_for_unreachable/3`
matches only `match?({:early_return, _, _}, stmt)`.

Verified: feeding
`{:block, [], [{:function_call, [name: "raise"], [...]}, {:function_call, [name: "Logger.info"], [...]}]}`
to `DeadCode.analyze/1` returns `has_dead_code?: false, total_dead_statements: 0`.
The *check* `MetaCredo.Check.Refactor.DeadCode` already handles both shapes via
`@terminators ~W(raise reraise throw exit return)` and `early_return?/1`
(`lib/metacredo/check/refactor/dead_code.ex:76-83`) — and its own docstring says
"`raise`/`throw`/`return` are emitted as plain `:function_call` nodes rather than
`:early_return` -- both shapes must be handled." The analysis module and the
check disagree.

**Fix:** add a second clause to the reducer predicate in
`check_block_for_unreachable/3` that also treats a `{:function_call, meta, _}`
whose `CheckUtils.safe_name(meta)` is in the terminator list as a terminator.
~4 lines; hoist the terminator list to `CheckUtils`.

### 2.2 **Defect** — `Purity.Effects.detect/1` classifies bare local calls by prefix, producing false impurity

`lib/metacredo/analysis/purity/effects.ex:71-95` — `time_function?("time" <> _)`,
`random_function?("rand" <> _)`, `network_function?("fetch" <> _)`,
`io_function?("read")`.

Verified: `Purity.analyze` on
`{:function_call, [name: "timeout"], [{:literal, [subtype: :integer], 5000}]}`
returns `{pure?: false, effects: [:time]}`. `timeout(5000)` is a pure timeout
value. The same module's `database_function?("update" <> _)` would classify a
local `update_counters/2` as a database effect.

This matters more than a single wrong answer because `Purity.walk_node/2`
(`lib/metacredo/analysis/purity.ex:96-105`) records anything *not* classified as
an `unknown` call and downgrades confidence to `:low` — so the module is noisy in
both directions at once.

**Fix:** require an actual module qualifier before the prefix match — only apply
`"time" <> _` etc. to names containing `"."`, and keep the bare-name table to the
unambiguous set (`puts`, `print`, `open`). The `@safe_modules` list in
`CheckUtils` already encodes the qualified-name convention; reuse
`CheckUtils.call_parts/1`.

### 2.3 **Defect** — `--only` / `--min-confidence` typos fail silently and exit 0

`lib/mix/tasks/metacredo.ex:283` — `parse_list/1` does `String.to_atom/1` with no
validation against `MetaCredo.Check.valid_categories/0`.
`lib/metacredo/issue.ex:117` — `parse_confidence/1` falls through to `nil`.

Verified: `mix metacredo --only securty` prints `running 0 checks on 106 files`
and `found no issues`, exit code 0. `mix metacredo --min-confidence hgih` runs all
52 checks with the filter silently disabled, exit code 0.
`Issue.parse_confidence("HIGH")` also returns `nil` (case-sensitive), so a user
who capitalises loses the filter.

A CI gate that silently passes because of a typo is the worst failure mode a
linter has.

**Fix:** in `parse_list/1`, intersect against `Check.valid_categories()` and
`Mix.raise` on any unknown atom, listing the valid ones. In
`parse_confidence/1`, add a `Mix.raise`-ing variant used by the Mix task (keep
the permissive one for programmatic callers), and `String.downcase/1` before
matching.

### 2.4 **Defect** — `Execution.run_checks_on_file/2` swallows every check crash with no user-visible signal

`lib/metacredo/execution.ex:196-207` — `rescue e -> Logger.warning(...); []`.

The rescue is correct in principle (one broken check must not kill the run) and
`execution_test.exs`'s `"survives a check that raises"` pins it. But the only
trace is a `Logger.warning`, and `mix metacredo` does not configure a Logger
backend in the CLI path. In a normal `mix metacredo` invocation the report says
"found no issues" while a check is silently dead, which is indistinguishable from
a clean codebase.

**Fix:** accumulate crashes into the report
(`%{report | check_failures: [{module, filename, exception}]}`) and have
`CLI.Output.print_footer/4` print `N check(s) crashed and were skipped` before
the summary. ~10 lines, no behaviour change to the happy path.

### 2.6 **Smell** — `Dialyzer` is configured but not gated, and `@dialyzer :no_opaque` is used to silence it

`mix.exs:24-30` configures `plt_file`, `plt_add_apps: [:mix, :ex_unit]`,
`list_unused_filters: true` — a real investment. `mix quality.ci` runs
`dialyzer`. But the project facts record Dialyzer as ✗, and
`lib/metacredo/analysis/duplication.ex:37` and
`lib/metacredo/analysis/duplication/similarity.ex:40` both carry
`@dialyzer :no_opaque`, which disables the opacity check for the entire module.

`similarity.ex` is the module whose `calculate/3` returns a `float()` documented
as "between 0.0 and 1.0" — exactly the contract opacity checking would help
verify.

**Fix:** run `mix dialyzer` and confirm it is green locally; if it is, the ✗ is a
stale signal and the `quality.ci` gate already covers it. If it is not green, the
`:no_opaque` suppressions are hiding the reason — scope them to the specific
function (`@dialyzer {:no_opaque, :calculate}`) rather than the module.

### 2.7 **Smell** — dead 4-tuple and 5-tuple clauses in the duplication walkers

`lib/metacredo/analysis/duplication.ex:224-262` — `walk_and_count/2` has clauses
for `{:binary_op, _, _, left, right}`, `{:unary_op, _, _, operand}`,
`{:conditional, cond, then_br, else_br}`, `{:loop, :while, cond, body}`,
`{:lambda, _params, _captures, body}`.

These are 4- and 5-tuples. Every other module in the repo — `Nesting`,
`Cognitive`, `Halstead`, `LoC`, `Similarity.count_nodes` — uses the uniform
3-tuple `{type, meta, children}` form, and `Analysis.Duplication`'s own docstring
says "All MetaAST nodes use the uniform 3-tuple structure". Verified the
4/5-tuple clauses never fire: a nested `binary_op` of 5 nodes reports `size: 5`
correctly, but via the generic 3-tuple fallback at line 264, not via the specific
clause.

**Fix:** delete the 4/5-tuple clauses. They are unreachable and they mislead
anyone reading the walker into thinking both formats are live.

### 2.8 **Smell** — `TagScan.comment_text/2` treats `#` inside a sigil as a comment start

`lib/metacredo/check/design/tag_scan.ex:143-160` — `do_find_marker/4` tracks `"`
and `'` but has no notion of `~s(...)`, `~r/.../`, heredocs, or charlists.

Verified: `TagScan.comment_text(~S{  @pattern ~r/FIXME#anchor/ }, :elixir)` returns
`"anchor/ "` — the `#` inside the sigil body is taken as the comment marker.

This does **not** currently produce a `TagFixme` false positive (verified a full
`TagFixme.run/2` on a module containing `@pattern ~r/FIXME#anchor/` returns `[]`),
because the sigil body has no `FIXME` *before* the `#`. But the extraction is
wrong, and the module's docstring claims "The extraction is string-aware: a
comment marker that appears inside a string literal ... is *not* treated as the
start of a comment." Sigils are string literals in Elixir.

**Fix:** add a `~` sigil case to `do_find_marker/4`: on seeing `~` followed by a
letter and a delimiter, skip to the matching closing delimiter. ~12 lines.

### 2.9 **Taste** — `Config.enabled_checks/1` has two near-identical `:all` clauses that diverge

`lib/metacredo/config.ex:189-204` — the first clause matches
`%{checks: %{enabled: :all, disabled: disabled}}` and uses the config's `disabled`
list; the second matches `%{checks: %{enabled: :all}}` (no `disabled` key) and
falls back to `default_disabled_checks()`. Because `normalize_config/1` always
supplies a `:disabled` key, the second clause is only reachable when a caller
hand-builds a config map — which `execution_test.exs` does in several places.

Fine either way, but the duplication means a change to one is easy to miss in the
other. Collapse to one clause with
`Map.get(checks, :disabled, default_disabled_checks())`.

### 2.10 **Taste** — `LoC.calculate/2` derives `physical` from `logical` when metadata is absent

`lib/metacredo/analysis/complexity/loc.ex:76` —
`physical = Map.get(metadata, :line_count, logical)`.

When a caller passes no metadata, `physical == logical` and `blank == 0` by
construction. The metric is then not "lines of code" but "statements". A caller
reading `result.loc.physical` has no way to tell a real count from a statement
count.

**Fix:** return `physical: nil` when metadata lacks `:line_count`, and let
`Result.check_loc/2` (which only reads `:logical`) be unaffected.

## 3. Codebase improvement ideas

Ordered by value-for-effort.

**3.1 — Raise the coverage floor to the measured value and ratchet it.**
`.github/workflows/ci.yml` sets `FLOOR=51` against a measured 54.1%. Change to
`FLOOR=54` with the existing comment made true. One-line change; prevents the
3-point regression the current floor permits.

**3.2 — Add `test/metacredo/analysis/complexity_test.exs` covering the six
metric modules.** These are pure functions over 3-tuple ASTs —
`Nesting.calculate/1`, `Cognitive.calculate/1`, `Cyclomatic.calculate/1`,
`Halstead.calculate/1`, `LoC.calculate/2`, `FunctionMetrics.calculate/1`. They
sit at 8–15% coverage across 1,971 lines. A table-driven test over ~10 ASTs per
module would lift all six at once. This is the single highest-value test
investment in the repo.

**3.3 — Hoist the terminator list to `CheckUtils` and use it in both dead-code
modules.** `@terminators ~W(raise reraise throw exit return)` currently lives only
in `lib/metacredo/check/refactor/dead_code.ex:76`. Moving it to
`CheckUtils.terminator?/1` lets `analysis/dead_code.ex` use it (fixing 2.1) and
gives one place to extend.

**3.4 — `propwise` candidates.** The project facts state "no Elixir files in
diff", so there is no diff-scoped candidate set to report. Were one to be
generated, the natural targets are the fingerprint/similarity pair, which have
genuine algebraic laws worth stating as properties in
`test/metacredo/analysis/duplication_test.exs`:

```elixir
use ExUnitProperties

property "exact/1 is reflexive over structure" do
  check all ast <- meta_ast_generator() do
    assert Fingerprint.exact(ast) == Fingerprint.exact(ast)
  end
end

property "normalized/1 is invariant under variable renaming" do
  check all name <- string(:alphanumeric, min_length: 1) do
    a = {:variable, [], "x"}
    b = {:variable, [], name}
    assert Fingerprint.normalized(a) == Fingerprint.normalized(b)
  end
end

property "similarity is symmetric and bounded" do
  check all a <- meta_ast_generator(), b <- meta_ast_generator() do
    s = Similarity.calculate(a, b)
    assert s >= 0.0 and s <= 1.0
    assert_in_delta s, Similarity.calculate(b, a), 1.0e-9
  end
end

property "identical ASTs have similarity 1.0" do
  check all a <- meta_ast_generator() do
    assert Similarity.calculate(a, a) == 1.0
  end
end
```

`Similarity.calculate/3` is documented as returning "a float between 0.0 and
1.0" — the symmetry and bounds properties are exactly what
`@dialyzer :no_opaque` (2.6) cannot check, and `similarity.ex` is at 18.3%
coverage.

**3.5 — Add `docs/` and project rules.** The facts record both as ✗. The repo has
excellent *inline* rationale but no `docs/` tree and no practices file. Given
`mix.exs`'s `extras` already lists `README.md`, `CI.md`, `LICENSE`,
`CHANGELOG.md`, adding a `docs/ARCHITECTURE.md` to `extras` costs one entry and
gives the 92 modules' layering (Checks → Execution → Sources → Metastatic) a
single home.

**3.6 — Delete the unreachable 4/5-tuple clauses** (2.7). Net-negative lines,
removes a misleading dual-format implication.

**3.7 — Make `Config.enabled_checks/1` a single clause** (2.9). Removes a
divergence hazard.

## 4. UX improvement ideas

Ordered by value-for-effort.

**4.1 — `--only` / `--ignore` must reject unknown categories.**
`mix metacredo --only securty` currently prints `running 0 checks on 106 files`
and exits 0 — a CI gate that passes because of a typo. Change `parse_list/1`
(`lib/mix/tasks/metacredo.ex:283`) to validate against
`MetaCredo.Check.valid_categories/0` and `Mix.raise` with the valid list. The
task already has this pattern for unknown switches (`parse_opts/1` raises
`"Invalid option(s): ..."`), so it is a consistent extension.

**4.2 — `--min-confidence` must reject unknown levels, and accept any case.**
`--min-confidence hgih` silently disables the filter (verified: full 52-check
run, exit 0). `Issue.parse_confidence("HIGH")` also returns `nil`. Add a
raising variant for the Mix task and `String.downcase/1` before matching.

**4.3 — Surface crashed checks in the report.** Today a check that raises
produces `Logger.warning` and a report that says "found no issues" (2.4). Print
`N check(s) crashed and were skipped` in the footer. Without this, a user cannot
distinguish "clean codebase" from "half the checks died."

**4.4 — `--diff` with no upstream branch is a silent no-op.** Verified:
`mix metacredo --diff` in a repo without `origin/main` prints
`No changed files found in diff, nothing to analyze.` then a normal-looking clean
report and exits 0. The default base is `origin/main`
(`lib/metacredo/git.ex:31`), which does not exist in a fresh clone. Add a
`git rev-parse --verify` pre-check on `base` and
`Mix.raise("--diff base ref 'origin/main' not found; pass --base <ref>")`.

**4.5 — `mix metacredo explain` has 0% coverage and no test.**
`lib/metacredo/cli/explain.ex` is 237 lines at **0.0%**. It is a user-facing
subcommand with four resolution paths (`file:line`, `file`, `FQN`, short name)
and a `@language_markers` table. Add
`test/metacredo/cli/explain_test.exs` exercising `resolve/1` for each of the four
forms — `resolve/1` is pure enough to test without driving compilation, which is
exactly why it was extracted.

**4.6 — `mix metacredo` on its own codebase reports zero issues, which is not
credible.** Verified: `mix metacredo --format json` on this repo returns
`{"summary":{"total":0,...},"issues":[]}` after 13.5s over 106 files with 52
checks. A 19,522-line codebase with zero findings from a 52-check suite means the
defaults are tuned to silence, not to signal. Consider a `--suggest` mode that
reports the disabled checks' findings at `:low` priority, so users can see what
they are opting out of.

**4.7 — The footer's priority legend is decorative.**
`lib/metacredo/cli/output.ex:334-341` prints `Showing priority issues: ^ ^ >`
with three colours, but `print_file_issues/1` renders a *category* label (`[S]`,
`[W]`, `[R]`) and never renders a priority glyph. The legend describes symbols
that do not appear in the output. Either render the priority glyph per issue or
change the legend to explain the category labels actually shown.

**4.8 — `explain` silently omits the examples section when language detection
fails.** `Output.print_explanation/3` (`lib/metacredo/cli/output.ex:145`) takes a
`language` argument and skips the `:examples` block entirely when it is `nil`.
Print `(no examples available for this project's language)` instead of nothing.

**4.9 — `--path test/` works but is undocumented at the point of failure.** The
`lift_test_exclusion` mechanism (`lib/metacredo/execution.ex:132-148`) is subtle
and correct. Add one line to the footer when `lift_test_exclusion` was active:
`(test/ trees included by explicit --path)`.
